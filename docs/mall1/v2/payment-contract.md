# Mall v2 Payment Contract

## 1. Purpose

This document defines the current Mall v2 payment boundary and the PG test integration used during development.

The PG test system is not a real payment gateway and is not the source of truth for Mall order state. It exists only to record test payment outcomes sent by the Mall.

---

## 2. Current Order Flow

The current Mall v2 order flow is:

```text
Cart
  -> create_order_from_cart(...)
  -> Order(PENDING)
  -> Payment step
```

`create_order_from_cart()` creates the order from the authenticated user's server-side Cart.

The order is created with:

- status: `PENDING`
- payment reference: `null`
- immutable OrderItem snapshot values
- stock deduction performed inside the existing order transaction
- Cart cleared only when order creation succeeds

Payment processing occurs after the order has been created.

---

## 3. Payment Source of Truth

Mall order state is owned by the Mall database.

The external PG test service does not directly determine or mutate Mall order state.

A PG test record with:

```json
{
  "isSuccess": true
}
```

means only that a test payment request was recorded as successful by the test service.

It must not be treated as sufficient proof by itself that a Mall order is `PAID`.

The Mall remains responsible for deciding whether an order transitions from `PENDING` to `PAID`.

---

## 4. PG Test Service

The current PG test system is a development/testing adapter.

Its responsibilities are:

1. receive a test payment result from the Mall,
2. authenticate the request using a shared test API key,
3. store the received test result in Firestore,
4. expose the recent test records for inspection.

It does not currently:

- execute a real payment,
- contact a production PG provider,
- update Mall orders,
- validate Mall order ownership,
- validate the order total against the Mall database,
- perform settlement,
- issue refunds.

---

## 5. PG Test Request Contract

The PG test API accepts a server-to-server `POST` request.

Authentication header:

```http
X-PG-Test-Key: <PG_TEST_API_KEY>
```

The server compares this value with the `PG_TEST_API_KEY` environment variable.

The comparison uses `timingSafeEqual`.

### Request body

```ts
type PgTestPaymentRequest = {
  saasName: string;
  id: string;
  isSuccess: boolean;
  amount: number;
  date: string;
};
```

Validation rules:

- `saasName`: non-empty string
- `id`: non-empty string
- `isSuccess`: boolean
- `amount`: finite number
- `date`: non-empty string

The exact semantic meaning of `id` must be confirmed by the Mall-side payment implementation before production payment integration is designed.

It may represent an order identifier or another merchant-side payment identifier, but this document does not assume either until the Mall caller is verified.

---

## 6. PG Test Response Contract

On success, the service returns HTTP `201`.

```ts
type PgTestPaymentResponse = {
  saasName: string;
  id: string;
  isSuccess: boolean;
  amount: number;
  date: string;
  callbackId: string;
};
```

`callbackId` is generated by the PG test service.

Format:

```text
cb_<random base64url value>
```

Unauthorized requests return HTTP `401`.

Invalid request bodies return HTTP `400`.

---

## 7. PG Test Persistence

Test records are stored in Firestore.

Collection:

```text
pgTestPayments
```

Stored shape:

```ts
type PgTestPayment = {
  callbackId: string;
  saasName: string;
  id: string;
  isSuccess: boolean;
  amount: number;
  date: string;
  createdAt: Date;
};
```

The document ID is the generated `callbackId`.

Recent records are loaded in descending `createdAt` order with a maximum of 50 records.

---

## 8. PG Test Monitoring Page

The test service includes a PG test monitoring page.

The page:

- loads the latest 50 test records,
- shows the total request count,
- shows the successful request count,
- shows the failed request count,
- renders the records in `PgTestPaymentTable`.

This page is for test observability only.

It does not represent Mall payment settlement state.

---

## 9. Expected Mall Test Payment Flow

The intended development flow is currently:

```text
Mall Order(PENDING)
        |
        v
User/test flow chooses success or failure
        |
        v
Mall server calls PG Test API
        |
        v
PG Test service records the result in Firestore
        |
        +---- failure ----> Mall keeps the order according to the Mall failure policy
        |
        +---- success ----> Mall performs its own trusted order transition
                            PENDING -> PAID
```

The exact Mall-side implementation of the final step must be confirmed from the existing `/payment` and related server code.

The PG test service must not be given authority to mutate the Mall database directly unless a future contract explicitly introduces such a trusted server-to-server boundary.

## 11. Amount Handling

The PG test API currently stores the `amount` supplied by its caller.

Therefore the PG test service is not an authoritative source for the Mall order amount.

Before a real payment or trusted payment-state transition is implemented, the Mall must validate the payment amount against its own immutable order total.

A caller-supplied PG test amount alone must not be used as proof that the correct amount was paid.

---

## 12. Order State Rules

Current relevant Mall order states include:

```text
PENDING
PAID
PROCESSING
SHIPPED
DELIVERED
CANCELLED
```

For the payment boundary covered by this document:

- `PENDING` means the order exists but payment has not been confirmed.
- successful payment processing is expected to transition the order to `PAID`.
- a failed PG test record does not automatically imply a new Mall order status.
- later lifecycle transitions remain governed by the existing Mall v2 order RPCs and server-side rules.

The exact RPC/server boundary used for the consumer payment success transition must be confirmed before this contract is marked complete.

---

## 13. Explicit Non-Goals

This contract does not define:

- a production PG provider,
- card or bank payment details,
- payment method storage,
- settlement,
- receipt issuance,
- real PG webhooks,
- payment cancellation,
- payment refund settlement,
- Point integration,
- chargeback handling.

Those require separate confirmed contracts.

---

## 14. Open Items

The following items must still be verified from the existing Mall payment implementation:

1. What `PgTestPayment.id` represents in the Mall flow.
2. Which Mall route calls the PG Test API.
3. How the Mall chooses test success or failure.
4. Which trusted server boundary transitions `PENDING -> PAID`.
5. Whether a payment reference is stored on the order after test success.
6. How duplicate payment attempts are handled.
7. Whether a successful test request is idempotent.
8. How the Mall verifies the test amount against the immutable order total.
9. What happens to a `PENDING` order after a test payment failure.

Until these are confirmed, the PG test adapter must remain classified as a development-only recorder rather than the Mall payment source of truth.
